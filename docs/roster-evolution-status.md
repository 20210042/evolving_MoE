# 회수되지 않는 헤드룸 — 연구 현황과 막힌 지점

서로 다른 역할의 에이전트를 자동으로 만들어 팀을 꾸리면 한 모델보다 잘할 것이라 보고
네 개 도메인에서 실험했습니다. 팀을 꾸리는 데까지는 되는데, 그걸 실제 성능으로 바꾸는
데서 계속 막힙니다. 어디가 잘못됐는지 봐주셨으면 합니다.

---

## 1. 하려는 것

모델 하나가 모든 문제를 잘 풀지는 못합니다. 그래서 서로 다른 성향의 에이전트 여러 명을 두고,
문제마다 맞는 쪽이 풀게 하면 전체가 올라갈 것이라는 발상입니다. 핵심은 그 역할들을
**사람이 정해주지 않는다**는 점입니다.

에이전트 한 명 = **시스템 프롬프트 한 덩어리**입니다. 모델도 파라미터도 전부 같고,
시스템 프롬프트만 다릅니다. 사용자 턴(문제 본문, 출력 형식 지시)은 전원이 완전히 동일합니다.
그래서 성능 차이가 나면 그건 시스템 프롬프트 때문입니다.

---

## 2. 진화 루프가 실제로 하는 일

범용 에이전트 **한 명**으로 시작합니다. 배치 하나가 문제 50개고, 한 판이 약 1,400스텝, 4시간입니다.

1. **로스터 전원이 배치 50문제를 각자 독립으로 전부 푼다.**
   이 단계에 라우팅은 없습니다. 9명이면 450번 생성합니다.

2. **채점해서 "아무도 못 푼 문제"를 모은다.**
   배치당 보통 13~23개 나옵니다. 이게 다음 역할을 찾는 재료입니다.

3. **그 문제들을 스카우트 LLM에게 보여준다.**
   문제당 *과제 설명 + 입력 + 실제로 틀린 답 3개*를 줍니다.
   **정답은 일부러 안 줍니다** — 주면 "정답을 그대로 써라"가 최적해가 되고,
   추론 시엔 정답이 없어서 그 에이전트가 무의미해집니다.

4. **스카우트가 새 시스템 프롬프트를 하나 만든다.**
   3문장 이하. 미리 준 분류체계(주제·난이도·오류유형)를 쓰지 말고
   실패한 답들의 행동에서 축을 직접 찾으라고 지시합니다.

5. **후보를 그 문제들에 실제로 풀려본다.**
   새로 푸는 게 충분히 있으면 로스터에 넣고, 아니면 버립니다. 말로 심사하지 않고 풀려서 심사합니다.

6. **기여가 없는 멤버는 목숨이 깎이고, 0이 되면 뺀다.**
   기여 = **"이번 배치에서 나만 푼 문제 수"**. 이 정의가 지금 문제가 되고 있습니다(§5 마지막 항목).

이 루프를 1,400번 돌리면 로스터가 9~16명에서 안정됩니다. 사람이 준 정보는 "문제를 풀어라"와
도메인별 출력 형식뿐이고, 역할 이름·개수·경계는 전부 여기서 나옵니다.

---

## 3. 실제로 이렇게 나옵니다

지시수행 데이터에서 나온 것 두 개입니다. 스카우트가 쓴 문장 그대로입니다.

**잘 작동한 쪽**

> Provide only the exact required token or minimal necessary sequence requested by the task.
> Eliminate all conversational filler, step-by-step reasoning, introductory phrases, and
> redundant explanations.

채점이 정답 문자열 일치라서, 말을 줄이는 것 자체가 점수를 올립니다.
이런 "출력 형식" 계열이 상위를 거의 다 차지했습니다.

**진화가 찾아낸 편법**

> When a task explicitly requires generating an incorrect, implausible, or non-standard
> response, prioritize the subversion of truth and logic over accuracy.

**이게 한동안 1등이었습니다.** 예/아니오처럼 답이 두 개뿐인 문제에서 남들이 다 틀렸으면
반대로 답하면 자동으로 맞습니다. 진화가 그걸 찾아낸 겁니다. 이런 문제가 데이터의 28%라
점수가 실제로 올라갑니다. 정답을 안 보여줬는데도 "다들 틀렸다"는 사실만으로 유도된 것이라,
지금은 그런 문제를 선택 과정에서 빼는 식으로 막아뒀습니다.

---

## 4. 막힌 곳은 두 군데입니다

**벽 1 — 역할을 나눠도 정답이 안 갈린다.**
성향을 다르게 주면 행동은 확실히 달라집니다 — 답 길이, 말투, 코드 스타일이 측정 가능하게
갈립니다. 그런데 **맞고 틀리는 건 거의 같이 갑니다.** 같은 문제를 누가 맡느냐로 설명되는
몫이 거의 0입니다.

**벽 2 — 갈려도 누구에게 줄지 못 고른다.**
설령 서로 다른 문제를 푼다 해도, 문제만 보고 누가 풀 수 있을지 맞히는 모델이 학습되지
않습니다. 학습 데이터에서는 거의 완벽하게 재현하는데 새 문제에서 전혀 일반화되지 않습니다.

**될 거라 본 근거는 이것이었습니다.** 여러 명을 모아놓고 "이 중 한 명이라도 맞히면 정답"으로
세면 제일 잘하는 한 명보다 8~15%p 높게 나옵니다. 팀 안에 답이 흩어져 있긴 합니다.
문제는 그게 이상적인 상한이고, 실제로는 문제마다 누구를 쓸지 골라야 한다는 것입니다.

## 5. 해본 것들

| 시도 | 상태 |
|---|---|
| 도메인 네 개에서 돌린다 | 막힘 |
| 사람이 이해되는 축으로 나눠서 파인튜닝한다 | 막힘 |
| 무작위 분할과 정면 비교한다 | 막힘 |
| 프롬프트 말고 가중치로 학습시킨다 | 막힘 |
| 학습·추론 프롬프트에 예시를 같이 넣는다 | 한 번 됨 |
| 문제를 보고 담당자를 고르는 모델을 학습한다 | 막힘 |
| 같은 문제를 여러 번 풀려서 운을 걷어낸다 | 막힘 |
| 답이 맞았는지 확인해주는 검증기를 붙인다 | 배제 |
| 진화의 선택 기준 자체를 바꾼다 | 진행 중 |

**도메인 네 개에서 돌린다** — 수학 서술형, 4지선다 상식, 코딩(테스트를 실제로 실행해 채점),
지시수행. 채점 방식이 서로 완전히 다른데 네 번 다 같은 자리에 도착했습니다.

**사람이 이해되는 축으로 나눠서 파인튜닝한다** — 문제를 LLM으로 과목 8개(생물·천문 등)로
태깅하고, 그 분류 그대로 전문가를 만들어 각자 자기 과목만 학습시켰습니다. 자동으로 찾은
분할보다 **더 나빴습니다.**

**무작위 분할과 정면 비교한다** — 인원수와 각자의 학습 데이터량을 정확히 똑같이 맞추고
배정만 무작위로 섞었습니다. **우리 분할이 무작위를 못 이깁니다.** 이어서 왜 그런지 봤더니,
진화를 돌릴수록 팀원들의 실패 패턴이 서로 더 비슷해지고 있었습니다 — 무작위 팀보다도
덜 다양합니다.

**프롬프트 말고 가중치로 학습시킨다** — "성향을 글로 주니까 약한 것 아니냐" 싶어, 진화가 찾은
분할대로 각 전문가를 따로 파인튜닝(LoRA)하고 실제로 생성시켜 채점했습니다. 프롬프트에서
안 나온 게 가중치에서도 안 나왔습니다. 게다가 어떤 조합도 **그냥 전체 데이터로 통짜
파인튜닝한 모델을 못 넘었습니다.**

**학습·추론 프롬프트에 예시를 같이 넣는다** — 전문가마다 자기에게 배정된 문제에서 뽑은
(문제, 정답) 2개를 프롬프트 앞에 붙여 학습시키고, 추론 때도 똑같은 2개를 붙였습니다.
**이때 처음으로 팀이 실제로 서로 다른 문제를 풀었고, 무작위 분할도 넘었습니다.** 다만 이
변경에 성향 프롬프트 추가가 같이 묶여 있어서 무엇이 원인인지 분리되지 않았고, 실제
배포에서는 벽 2에 막혀 그 이득이 그대로 사라졌습니다.

**문제를 보고 담당자를 고르는 모델을 학습한다** — 세 갈래로 시도했습니다. 문장 임베딩,
모델 내부 표현(hidden state), 그리고 각 전문가가 스스로 낸 확신도. 전부 "제일 잘하는 한 명으로
고정"보다 나아지지 않았습니다. 내부 표현 라우터는 학습 데이터에서는 정답 배정을 거의 그대로
재현하는데, 새 문제에서는 완전히 무너집니다.

**같은 문제를 여러 번 풀려서 운을 걷어낸다** — 한 번 생성한 결과로 "얘만 풀었다"를 판정하는 게
노이즈 아니냐는 지적이 있어, 같은 (전문가, 문제) 쌍을 5번씩 다시 풀렸습니다. 노이즈는
실재했습니다 — 절반 이상이 시도마다 결과가 갈렸습니다. 그런데 걷어내고 봐도 **성향으로
설명되는 몫은 여전히 0에 가까웠고, 대부분이 문제 자체의 난이도였습니다.**

**답이 맞았는지 확인해주는 검증기를 붙인다** — 벽 2를 우회하는 가장 직접적인 방법입니다.
코딩은 테스트를 실행해보면 되니 특히 쉽습니다. 그런데 그러면 "역할 분화가 이득을 만든다"가
아니라 "검증기가 이득을 만든다"가 되어 연구 취지를 벗어난다고 보고 접었습니다.

**진화의 선택 기준 자체를 바꾼다** — 지금까지 기여도가 "이번 배치에서 나만 푼 문제 수"였습니다.
팀이 커지면 "정확히 나 혼자만" 맞히는 사건이 구조적으로 희박해져서, 대부분의 스텝에서 거의
전원이 0점입니다. 그래서 **"내가 푼 문제마다, 나 말고 못 푼 사람의 비율"**로 바꿔 연속적으로
재고 있습니다. 바꾸자마자 위에 올라오는 성향이 실제로 달라졌습니다 — 도메인이나 프롬프트가
아니라 **선택 기준을 바꿔서 결과가 달라진 건 이번이 처음**입니다.

## 6. 지금 확실히 말할 수 있는 것

- 시스템 프롬프트를 바꾸면 **행동은 바뀝니다.** 여러 방식으로 확인했고 확실합니다.
- 그런데 그 차이가 **맞고 틀림과 정렬되지 않습니다.** 푸느냐 마느냐는 대부분 문제 자체의
  난이도와 생성 과정의 운으로 설명되고, 누가 맡았느냐로 설명되는 몫이 거의 없습니다.
- 여러 명을 모으면 커버리지가 오르는 건 사실이지만, **같은 프롬프트를 여러 번 돌린 것과
  통계적으로 구별되지 않습니다.** 같은 에이전트를 12번 복제한 팀과 진화한 12명 팀의
  커버리지가 사실상 같았습니다.
- 예외적으로 효과가 났던 경우는 "누구인가"가 아니라 **"무엇을 보여주는가"(예시),
  "언제 개입하는가"(틀린 답을 본 뒤 고치게 하기)** 쪽이었습니다. 후자는 개입하는 에이전트가
  누구든 효과가 같았습니다.

## 7. 여쭙고 싶은 것

**Q1. 전제 자체가 틀린 걸까요?**
"성향을 나누면 푸는 문제도 나뉜다"가 출발점인데 네 도메인에서 부정됐습니다.
진화 방식이 나쁜 건지, 애초에 성립하지 않는 가정인지 판단이 안 섭니다.

**Q2. 담당자를 고르는 문제를 다르게 볼 방법이 있을까요?**
지금은 "문제를 보고 누가 풀지 예측한다"로 놓고 풀었고 실패했습니다.
검증기는 취지상 배제했습니다. 이 둘 말고 다른 각도가 있을지 모르겠습니다.

**Q3. 선택 기준을 바꾸는 쪽이 승산이 있어 보이시는지요.**
지금 유일하게 반응이 온 축입니다. 다만 "선택 기준을 이렇게 바꿨더니 다른 성향이 뽑히더라"가
최종 성능으로 이어질지는 아직 모릅니다.

**Q4. 역할 분화가 통할 데이터는 어떤 모양일까요?**
지금까지 "여럿을 모았을 때 커버리지가 많이 오르는" 데이터를 골랐는데, 그 기준이 잘못됐다는 걸
뒤늦게 알았습니다(그 상승분이 그냥 여러 번 시도한 효과였습니다). 무엇을 기준으로 도메인을
골라야 할지 모르겠습니다.

따로 정리돼 있으니 필요한 부분만 말씀 주시면 그것만 드리겠습니다.
